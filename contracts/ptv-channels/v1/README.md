# PTV Channels API contract v1

This is the machine-readable companion to the [approved architecture RFC](../../../docs/architecture/PTV_CHANNELS_RFC_V1.md). It specifies the proposed Plugin HTTP interface; no Channels route, scheduler, player integration, or deployment is implemented by these files.

## Contract files

- `http-contract.json` maps the nine operations to methods, paths, typed path parameters, request/query/response schemas, cache headers, conditional writes, and stable error status codes. The guide query schema requires UTC `fromUtc` and `toUtc`; the manifest caps their interval at 24 hours.
- `*.schema.json` use JSON Schema 2020-12. `entry.schema.json` is shared by list Now/Next and guide. `admin.schema.json` exposes the write, read, list, and preview shapes through its `$defs`.
- `fixtures/user-success.json`, `user-errors.json`, and `admin.json` contain HTTP examples, including two user projections of one shared program. `fixtures/invalid.json` derives rejection cases from those examples. `fixtures/compatibility.json` covers an older Plugin with no capability route at the transport boundary.
- `npm run contracts:validate` compiles the schemas and checks the fixtures, status/code pairs, redaction, UTC windows, revision headers, and timeline arithmetic.

The base path is `/Ptv/v1/channels`, separate from Jellyfin `/LiveTv/*`. Every route requires an actual authenticated Jellyfin user. Admin routes require that user to have administrator policy; an elevated API key without a resolved user is insufficient. User-specific responses, including capabilities and admin reads, use `Cache-Control: private, no-store`. The response `serverTimeUtc` is a clock sample, not a reservation or playback session.

## V1 wire decisions pinned at this gate

The approved RFC defines consumer payloads and logical admin resources. These schemas pin the remaining admin field names and envelopes:

- Admin write bodies are `{contractVersion, resourceType, resource}`. The path uses `definitions`, `collections`, or `blocks`, while `resourceType` uses `definition`, `collection`, or `block`. POST creates an opaque ID. PUT identifies the resource in the path and requires a quoted `If-Match` revision; server-owned IDs, revisions, and `scheduleAnchorUtc` are absent from write bodies.
- Admin single-resource responses add `serverTimeUtc` and return the effective resource with its ID and revision. GET, POST, and PUT return an `ETag` equal to that revision. List responses use `{contractVersion, serverTimeUtc, resourceType, resources}` and have no ETag.
- A definition supplies `name`, IANA `timeZone`, `enabled`, and ordered `blockAssignments` containing block IDs. A collection supplies `libraryIds`, one `mediaType`, optional series/genre/tag/duration predicates, and `orderingPolicy: "stableId"`; the block's `selectionMode` controls program selection. A block supplies weekday names, `localStart` as `HH:mm:ss`, elapsed `windowDurationMs`, `collectionId`, `selectionMode`, and optional `repeatWindowMs` from zero to seven days. Omitting it on a write applies the 24-hour default; readback always returns the effective value.
- Preview takes an existing `channelId` and a UTC window of at most 48 hours. It may include one draft admin write body. A draft block or collection replacement also names `candidateResourceId`; a draft definition applies to `channelId`. Without a draft, preview uses committed resources. Its entries are **candidate** slots without durable program IDs, entry revisions, or cursor advancement. `inputHashSha256` records the observed collection input used for that calculation.
- A playable list/guide entry may include `title`, `seriesTitle`, and `description` after user-aware lookup. An unavailable or gap entry omits those known metadata fields. No list or guide entry contains `itemId`; among user-facing routes, only a successful resolve returns one. Artwork is deferred until a user-scoped image transport can avoid revealing Jellyfin item IDs or private metadata. Admin preview may include candidate item IDs for its authenticated administrator. Resolve requests accept exactly `contractVersion` and either both expected entry identifiers or neither. They cannot supply user, clock, item, or offset values.

Response readers accept additive unknown fields; request writers emit only declared fields. A v1 publisher serializes only reviewed fields from an explicit allowlist. Unknown response extensions must pass the same user-scope and redaction review before being emitted; reader tolerance is not permission to publish them. Optional data is omitted rather than sent as `null`. UTC timestamps end in `Z`; positions and durations are integer milliseconds; IDs and revisions are opaque. A future incompatible field or meaning change requires a new major contract directory.

The schemas check payload shapes. The fixture validator also checks relationships that JSON Schema cannot express, such as `positionMs = serverTimeUtc - startUtc`, ordered guide entries, the guide and preview window caps, ETag/revision equality, and status/code pairing. Its known-ID scan proves that these fixtures do not embed their example Jellyfin item IDs in list, guide, or error strings; it cannot prove arbitrary runtime output is safe. An older Plugin may answer capability discovery with its own 404 format, outside the Channels error envelope; clients treat an absent route as unsupported. Actual user authorization, cache isolation, Jellyfin playback negotiation, DST expansion, storage recovery, and physical-device behavior remain separate acceptance gates. This contract package supplies no evidence that those runtime gates have passed.
